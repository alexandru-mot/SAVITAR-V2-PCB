Geometric reaction time

What this number is. Purely the time for the robot to physically travel the distance between the sensor array and the wheel axle. It is the window you have before the wheels arrive at the point the sensors just read — not the electrical or software response time, which is entered separately above and subtracted afterwards.

Required loop frequency

Frequency needed to fit 5, 10 or 20 controller updates inside the geometric window at the current speed and arm length. Compare against your configured loop rate.

Differential drive on a curve

Model and assumptions

Standard kinematic differential-drive model, with the robot treated as a rigid body rolling without lateral slip:

v = (v_right + v_left) / 2 ω = (v_right − v_left) / L R = (L/2)·(v_right + v_left)/(v_right − v_left)

Solved in reverse here: you give the track radius R and forward speed v, and it returns the wheel speeds needed. Equal wheel speeds are handled explicitly — ω = 0 reports an infinite radius rather than dividing by zero.

Assumes: no wheel slip, no tyre scrub, point contact patches, rigid chassis, and that both motors actually reach the commanded speed. Real silicone tyres 22 mm wide scrub noticeably in tight turns, so treat this as a first-order figure.

Curve tracking

Model and assumptions

With the array rigidly mounted A ahead of the axle, a curved line does not stay centred on the array. Taking the path as a circle of radius R tangent to the robot heading at the axle centre, the line crosses the array plane offset laterally by:

offset = R − √(R² − A²) ( ≈ A²/2R for R ≫ A )

The line stays inside the array only while that offset is under the half-span s, which gives a tightest trackable radius of:

R_min = (A² + s²) / (2s)

This is the geometric trade-off behind the arm length: a longer arm buys reaction time and costs tight-curve capability, growing as A².

Assumes: steady-state cornering with the robot already aligned to the curve, and the array plane perpendicular to the heading. During entry into a curve the real offset is larger, so treat R_min as optimistic.

Reference

Reaction-time definition
t_react [ms] = A [mm] / v [m/s]

The units cancel conveniently: millimetres divided by metres per second lands directly in milliseconds. At A = 80 mm and v = 2 m/s that is 40 ms, and at a 1 kHz loop rate roughly 40 controller updates fit inside it.

Sensor pitch and resolution
span = outer-sensor centre-to-centre distance pitch = span / (n − 1) x_i = −span/2 + i·pitch i = 0 … n−1

Raw quantisation is one pitch, worst-case error half a pitch. Weighted-centroid interpolation across the analogue readings does better, by roughly the interpolation factor set in the assumptions panel — that factor is a placeholder for your own bench measurement, not a specification.

Curved array geometry
θ_half = asin( chord / 2R ) θ_i = −θ_half + i·(2θ_half)/(n−1) x_i = R·sin θ_i y_i = A ∓ R·(1 − cos θ_i)

The chord is held equal to the straight-array span so lateral coverage stays comparable. Each sensor then sits at its own longitudinal position, so each has its own reaction time — the spread between the centre and outer sensors is reported in the array panel.

Whether that helps depends on your controller. A forward bow gives the centre sensors the longest lead; a backward bow gives it to the outer ones, which are the sensors that matter when the line is already running away from you. Neither is inherently better, and both cost you a slightly longer array arc for the same width.

Drivetrain speed ceiling
v_noload = (rpm_out / 60) · π · D / 1000 [m/s]

No-load figures only. Under load the motor sits somewhere on its torque–speed curve, so the achievable speed is lower — how much lower depends on rolling resistance, drivetrain losses and how hard you are accelerating. The percentage shown next to your target speed is a rough duty indicator, not a PWM setting.
